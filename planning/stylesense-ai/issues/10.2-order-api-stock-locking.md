# 10.2 — Order Placement Service, Mock Gateway, and Orders API

**What to build:** `POST /api/orders/` turns the caller's own cart into an order inside **one** transaction: lock every product row with `select_for_update()`, re-validate stock against those locked rows, decrement, charge, write the order, empty the bag. The client sends no amounts, no line ids, and no cart contents — the server reads its own cart and re-totals it from live prices, reusing `cart_service.calculate_totals` and `line_unit_price` rather than growing a second implementation of the money math. Plus `GET /api/orders/` and `GET /api/orders/<id>/`, scoped by user exactly the way cart items are.

**Blocked by:** 10.1 — Order Models

**Status:** done

## Decisions

**Partial stock failure fails the whole order.** One short line aborts all of it,
but the 409 carries *every* failing line — product, variant, requested,
available, and whether it was `insufficient_stock` or `unavailable` — so the UI
can annotate each offending row instead of making the customer rediscover them
one at a time. Stock is checked per *product* summed across lines: the same
shirt in M and L are two lines drawing on one pool, and checking them
independently would happily sell two units of a one-unit product.

**The mock gateway declines on demand.** `payment_service.charge` sleeps for
`MOCK_PAYMENT_LATENCY_SECONDS` (default 1.2) and raises `PaymentFailed` when
handed the sentinel `tok_decline`. An always-succeeds stub would have left the
rollback path — the only genuinely interesting engineering in this epic —
permanently untested.

**Payment is charged inside the transaction, holding the row locks.** A
high-volume shop would refuse to do this: it would reserve stock in one
transaction, charge outside it, and compensate on failure. That trade buys
throughput at the cost of a compensating path that can itself fail. Here a
genuinely atomic rollback is worth more than lock-hold time, and the choice is
commented at the call site.

**No `pending` or `failed` status.** Neither could ever be observed. Placement is
one transaction with the charge inside it, so a decline rolls everything back and
no row survives to be marked failed. An order exists only if it was paid for.

- [x] `services/payment_service.py` — fake gateway, artificial latency, `DECLINE_TOKEN` sentinel
- [x] `services/order_service.py` — `place_order`, `get_orders`, `get_owned_order`, `advance_status`
- [x] Products locked with `select_for_update()` **in ascending pk order** — two orders sharing products would deadlock if they took the same rows in different sequences
- [x] Every cart line is re-pointed at the locked row before any money is computed; the prefetched copies are pre-lock reads another transaction may already have changed
- [x] Stock decremented with `F("stock") - quantity`
- [x] `OrderError` subclasses → `EmptyCart` 400, `StockConflict` 409 (+ `lines`), `PaymentFailed` 402 (+ `code`)
- [x] 409 not 400 for stock: the request was well-formed and was valid when the customer sent it — the world moved
- [x] `GET /api/orders/` and `/api/orders/<id>/`, lookup scoped by `user=request.user` so another user's id 404s

## Proving the lock — demonstrated, not asserted

Two threads, one unit of stock, released on a `threading.Barrier` so they enter
placement on the same instant, with gateway latency raised to 0.5s to hold the
critical section wide open.

**With the lock** (repeatable across runs):

```
cart-intruder@test.com   OK   SS-20260822-YP5Z total=6754.00
cart-verify@test.com     FAIL StockConflict — requested 1, available 0
stock after: 0 | orders created: 1 | loser's cart: still 1 row
```

The second thread blocks inside `select_for_update()` until the first commits,
re-reads `stock=0`, and raises cleanly.

**Control run, identical script with `QuerySet.select_for_update` neutered:**

```
cart-intruder@test.com   OK   SS-20260822-9KCB total=6754.00
cart-verify@test.com     ERROR IntegrityError: violates check constraint
                               "products_product_stock_check"
```

Both threads validated against a stale `stock=1` and both tried to decrement.
Worth being precise about what saved it: the *oversell* was blocked by Postgres's
own `CHECK (stock >= 0)` on `PositiveIntegerField`, not by the application — so
the customer got an unhandled `IntegrityError`, i.e. a 500. **What
`select_for_update()` buys is turning that crash into a correct, well-formed
409.** Which of the two threads loses varies run to run; with the lock it never
varies that both outcomes are correct.

## Verified over HTTP

- Unauthenticated POST and GET → 401
- Empty bag → 400 `"Your bag is empty."`
- 3-line bag (₹28,466 subtotal / ₹2,282 discount / ₹26,184 total) placed → 201 with
  frozen totals matching the cart exactly, `list_price` **and** `unit_price` per line
  (₹4,102 → ₹2,961 on the discounted jacket), `payment_reference` set, cart emptied
- **Decline** (`tok_decline`) → 402 in 1.27s, and afterwards: stock unchanged, no
  order row, all 3 cart lines intact. Across a decline *and* a success, stock moved
  by exactly one order's worth (79→76, 69→67)
- **409**: starved one product to 1 unit and delisted another behind the customer's
  back → both lines reported in one payload, correctly split into
  `insufficient_stock` vs `unavailable`; orders count and stock unchanged
- Ownership: bob GETting alice's order id → 404, identical to a nonexistent id;
  `GET /api/orders/` as bob → `[]`
