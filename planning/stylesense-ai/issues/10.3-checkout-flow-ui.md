# 10.3 — Checkout Flow UI

**What to build:** The `/checkout` route, and the wiring that makes the Checkout button do something. `CartSummary` has accepted an `onCheckout` prop since 8.4 that nothing ever passed — the button rendered enabled and was dead. This slice gives it a destination, adds the mock payment step, renders each of the three placement failures differently, and shows the confirmation.

**Blocked by:** 10.2 — Order Placement Service, Mock Gateway, and Orders API

**Status:** done

## Decisions

**A route, not a modal.** The checkout state has real error surfaces (a decline,
a per-line stock conflict) and a confirmation, all of which need room and a URL.
Both the cart page and the drawer point at it.

**No optimistic update on placement.** Every cart mutation applies locally and
rolls back on error, because the client can predict the outcome. This one can't:
success depends on stock the client hasn't seen and a payment that hasn't
happened. Showing a confirmed order before the server confirms it would be
showing a purchase that may not exist.

**The three failures are three different UIs**, because they are three different
events: a decline is retryable on the spot, a stock conflict sends the customer
back to fix their bag, and an empty bag means they shouldn't be on this page at
all (it redirects to `/cart`). `parsePlaceOrderError` turns the HTTP status into
a discriminated union so the page switches on `kind` rather than on status codes.

- [x] `api/orders.ts` — `Order`/`OrderItem`/`StockConflictLine` types, `placeOrder`/`fetchOrders`/`fetchOrder`, `DECLINE_TOKEN`, `parsePlaceOrderError` → `PlaceOrderFailure` union
- [x] `hooks/useOrders.ts` — `useOrders`, `useOrder`, `usePlaceOrder`
- [x] `usePlaceOrder` **clears the `["cart"]` cache on success** (writes `EMPTY_CART` through immediately so the header badge drops in the same frame, then invalidates), and invalidates `["products"]`/`["product"]` because stock just moved
- [x] It also invalidates cart + products **on error** — a 409 means the catalog moved underneath the bag, and the customer should retry against what's actually there
- [x] `pages/Checkout.tsx` — order review, mock card block, "simulate a declined payment" toggle, spinner during the gateway pause, confirmation state
- [x] `CartSummary`'s dead `onCheckout` prop finally passed from `Cart.tsx`
- [x] `CartDrawer` footer split: primary **Checkout** straight to `/checkout`, secondary **View Bag**
- [x] `/checkout` route inside `ProtectedRoute`
- [x] `EMPTY_CART` exported from `useCart.ts` for the post-order cache write

## Verified in the browser

- Cart → **Checkout** → `/checkout`, summary matching the bag exactly (₹28,466 subtotal / ₹2,282 discount / ₹26,184 total, 2 lines, 5 units)
- **Success:** Pay ₹26,184 → spinner for the gateway pause → confirmation with `SS-20260822-QSEM`, 5 items, Processing, ₹26,184. Header badge → 0 in the same frame, drawer shows "Your bag is empty". Stock moved 67→65 and 76→73, exactly one order's worth
- **Decline:** ticked the toggle → 402 banner *"Your card was declined. Nothing was charged and your bag is intact."*, still on `/checkout`, badge still 1, bag intact — and stock verified unchanged (65/73) with no order row created
- **Stock conflict:** set the product's stock to 0 behind the UI, then paid → per-line notice *"Premium Wool Jackets (Navy · M) — you asked for 1, only 0 left"* plus an **Edit your bag** link. Nothing charged
- Empty bag at `/checkout` (arriving by URL) → empty state with Continue Shopping
- Mobile 375px: no horizontal overflow

## Note

The MCP browser's `form_input` sets a checkbox's DOM `.checked` without firing
React's `onChange`, so the first decline attempt silently placed a real order
instead. Toggling it with an actual click is what exercises the controlled
input. Not an app bug — recorded so the next person driving this page in a
headless browser doesn't lose the same twenty minutes.
