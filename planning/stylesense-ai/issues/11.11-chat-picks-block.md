# 11.11 — Chat Picks Block and Unified Product Card

**What to build:** Break the AI's recommendations out of the assistant bubble into an attributed block with room for a rationale and an Add to Bag, and collapse the catalog and chat cards into one component.

**Blocked by:** 11.4 — Image Rendering; 11.10 — Chat Rationale Contract

**Status:** ready-for-agent

Prototype: branch **`prototype/beautiful-stylesense`** (commit `3680b78`), not on `main`. `git checkout prototype/beautiful-stylesense` then `pnpm --dir frontend dev` and open `/prototype/chat-cards?v=a|b|c|d`. Nothing to delete when this ships — the branch stays unmerged.

## Decisions

**The picks leave the bubble and become their own block.** The prose stays in the assistant bubble; recommendations render below it as a separate block attributed by an indigo left rail and headed `N picks for you`. Today the strip sits *inside* a `max-w-[70%]` bubble at 160px per card.

Rationale is what separated the four layouts built. In a full-bleed strip or a wrapping grid the `✦` line must clamp to two lines or the cards go ragged — *"The relaxed shoulder works with the wide-leg trousers you saved…"* truncates mid-thought. The detached block gives it a full line while keeping the photograph at ~210px. A layout that truncates the rationale is fighting 11.10. The block header also fixes the single-pick case: one lonely card in a wide column reads like a rendering bug, whereas `1 pick for you` reads deliberate.

**Accepted cost: a message is no longer one bubble.** A turn is now prose plus an attributed block, which touches how REST history rebuilds a conversation.

**Skeletons are sized by counting markers as the text streams.** The `products` event arrives *after* the text finishes, so the naive options are an empty gap then a pop-in, or a guessed skeleton count. Neither is necessary: the `[[product:12]]` markers stream **inline with the text**, and `ChatBubble.tsx:11` already parses them out before render. The browser already knows how many products are coming, and in what order, and currently throws that away. Count them, render exactly that many skeletons, fill on the event — the block reserves its true height and never jumps. **Degrade path:** if marker-counting proves unreliable on either provider, fall back to a fixed count rather than an empty gap.

**Mobile renders the block as editorial rows** — small 4:5 image left, brand / name / rationale / price / action right. At 375px a ~210px grid does not fit, and rows are the only narrow layout keeping the rationale on a full line. Full-width tall cards are prettier and much worse to scroll past: three picks push the chat input far off-screen, fighting the medium.

**One card component with optional slots.** `ProductCard` and `ChatProductStrip`'s mini card are separate files duplicating image, brand, name, price, discount strike-through and save heart — and 11.4 already deletes a `getGradient` duplication between them. After 11.3 and 11.6 they converged further without anyone intending it: both are 4:5, and the sizes are close (catalog ~290px, chat ~210px). What genuinely differs is a **rationale** and an **Add to Bag** — two optional slots, not two components. Rejected: giving the catalog grid Add to Bag as well, which reopens the size/colour problem across 50 cards for a capability nobody asked for.

**Add to Bag expands the card into a picker.** It is not a preference: `cart_service._validate_variant` rejects a bag line whenever the product has sizes or colours and the request omits them, and every catalog product has both — so a one-click add returns `InvalidVariant`, always. Clicking expands the card into a size grid, plus a colour row when needed. Accepted cost: expanding one card in a grid makes its row taller and pushes content below it down — downward, away from the reader's focus. Rejected: a popover, which avoids the shift and needs portalling plus collision positioning (see the epic's `backdrop-filter` decision). Rejected: routing to the product page, which makes the button a duplicate of the link already on the card.

**Confirmation is inline; the cart drawer does not open.** The button becomes `✓ In your bag` and the sticky header bag badge increments. This deliberately departs from `ProductDetail.tsx:79`, which does `onSuccess: () => openDrawer()` — a pattern set on a page where the shopper is *finished*. A chat message holds up to five picks with a rationale on each; a shopper adding the second still has three to read, and a full-height drawer covers exactly the content they are working through. The whole point of putting Add to Bag on the card was acting *without leaving the conversation*.

**The out-of-stock card state stays even though 11.10 filters retrieval.** Stock can reach zero between the reply arriving and the click — `cart_service._assert_stock` rejects the add whatever the card shows — and history replays old picks that `ChatMessage.products` has no idea went out of stock.

**The block can never exceed five cards.** `ContextBuilder(top_k=5)` plus the prompt's "cite each product at most once per reply". No display cap is needed; revisit if `top_k` rises.

- [ ] One card component serving catalog and chat, with optional rationale and action slots

- [ ] Add to Bag expands into a size/colour picker; inline `✓ In your bag` confirmation
