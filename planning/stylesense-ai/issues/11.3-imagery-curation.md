# 11.3 — Product Imagery: Curation and Seeding

**What to build:** Hand-map one curated editorial photograph to each of the 50 catalog products, plus four more for the home page, and make the seed path write `ProductImage` rows idempotently.

**Blocked by:** —

**Status:** ready-for-agent

Sourcing research: `docs/research-product-imagery-sources.md`.

## Decisions

**Unsplash primary, Pexels as gap-filler, Pixabay ruled out.** The plan hotlinks a permanent URL into the database forever. Unsplash's API Guidelines *require* hotlinking, Pexels permits it, and **Pixabay's API docs explicitly forbid** permanent hotlinking — which would force downloading and self-hosting all 50. Unsplash is also the only source with a documented on-the-fly resize pipeline on a permanent URL (imgix `w`, `q`, `fm`, `auto=format`, including WebP/AVIF negotiation); Pexels's URLs look similar but resizing-by-param is observed convention, not a documented contract.

**The old `source.unsplash.com` random endpoint is dead.** Deprecated 2021-11-25, sunset from 2024-06-11, per Unsplash's own changelog. Do not use it or any tutorial referencing it.

**`ProductImage` is the single source; `Product.image_url` is deleted.** Three image fields exist and only one is real. `Product.image_url` is referenced by zero serializers. `ProductImage` already feeds both live consumers — `ProductDetailSerializer` and `ProductCardSerializer.get_image_url()`, which picks `is_primary` or falls back to the first row. `OrderItem.image_url` is a purchase-time snapshot and is untouched. The dead field is removed rather than left as a trap for someone to populate the wrong thing.

**One photo per product, sourced at 4:5.** Gallery views are derived from that same photo as imgix crops, so the garment is guaranteed identical — see the epic's decision. 4:5 because the product page is where cropping hurts most and `ImageGallery` is already `aspect-[4/5]`.

**The 50 URLs live in `docs/products.json`.** Alongside `sizes` and `colors`, which are already per-product arrays of the same shape. One file, one command, one place a product's data lives. A slug-keyed second file drifts the moment a product is renamed.

**The seed path must be idempotent independently of the product.** `seed_products.py` creates **no `ProductImage` rows at all** — the table has never been written to by anything — and its `get_or_create(defaults=...)` skips every existing product on re-run. Bolting images onto that path would populate nothing on an already-seeded database.

**Attribution is one footer line, not per-photo bylines.** Neither the Unsplash nor the Pexels *License* requires attribution, but Unsplash's *API Guidelines* make it mandatory the moment a photo is sourced through their API. A footer line holds whichever way the curation actually happens, and photographer names on a product page break the fiction that these are the store's own garments. **If this curation pass ends up scripted through the Unsplash API rather than hand-browsed, full per-photo attribution with profile links is the compliant answer — confirm the sourcing method before relying on the footer line.**

**Four editorial photos for the home page** — one hero, three for The Edit tiles — sourced and hotlinked the same way, referenced from frontend constants. Rejected: a settings row to hold a hero URL (needs a model this epic has ruled out) and reusing a product photo as the hero (a garment shot in a full-body editorial composition it was not shot for). `Category.image_url` stays unused; the Edit tiles are filtered `/shop` links, not categories.

- [ ] `images` array added to each entry in `docs/products.json`
- [ ] `seed_products.py` writes `ProductImage` rows, idempotent even when the product already exists
