# 11.5 — Faceted Search API

**What to build:** Turn the single-value product filter into real faceted search — multi-select facets, live counts, a sort control, and pagination that can actually report a total.

**Blocked by:** 11.4 — Image Rendering: Serializer, Ratios, and Fallback

**Status:** ready-for-agent

Research: `docs/research-faceted-search-django.md`.

## Decisions

**`CursorPagination` is retired for `PageNumberPagination`.** `ProductPagination` is a `CursorPagination` with `ordering = "-created_at"`. Cursor pagination **returns no `count`** — that is the trade it makes by design — and it requires its ordering field to be monotonic and effectively unique. Both properties block 11.6: the filter bar shows a result count beside facet counts, and today `Products.tsx` prints `products.length`, the number *loaded so far*, so it reads "12 products" while the facet next to it says `Dresses 6`. A user-selectable `price` sort breaks the ordering requirement outright. Cursor pagination solves drift under insertion on large mutating datasets; this catalog is 50 static rows. `useInfiniteQuery` is unaffected — `getNextPageParam` returns `page + 1`.

**Facets ride on the list response**, shaped `{ count, next, previous, results, facets }`. Results and counts are one answer to one query and should arrive as one payload; 11.6 renders them together in one 56px bar, so a separate endpoint means two in-flight requests describing two moments and a visible disagreement in the component whose job is telling the shopper the truth. The cost is ~1KB of redundancy per Load More, since counts describe the filter set rather than the page. Frontend reads them at `data.pages[0].facets`.

**Within-facet OR, across-facet AND — via `has_any_keys`, not `__contains`.** `colors` and `sizes` are plain `JSONField`, not `ArrayField`, so `__overlap` does not exist on them. The existing `__contains=[value]` only works because it is always called with one element: extend it to `colors__contains=["Black","White"]` and Postgres `@>` silently means **AND**, because containment requires the left array to hold *all* of the right's elements. `has_any_keys` compiles to Postgres `?|`, which matches top-level keys **or array elements**. This is a correctness trap, not a style preference.

**Counts reflect every *other* active facet.** Selecting Women updates the Category counts while Gender's own counts hold, so another gender can still be added. One `.aggregate()` per facet dimension with `Count("id", filter=Q(...))`. Verified working in 11.6's prototype.

**`Recommended` means `-rating, -created_at`.** Allow-list: `recommended`, `price`, `-price`, `-rating`, `-created_at`. `rating` is populated across all 50 products, needs no join, and gives a stable ordering — which matters now that a sort field is also a pagination ordering field. Rejected: true best-seller popularity from `OrderItem`. The rows exist and it is computable, but a demo database has almost no orders, so the ordering would be near-random under a confident label — and worst on the *default* sort, the one nobody chooses and everybody sees. Also rejected: personalising `Recommended` from the user's profile, which changes what a control means by auth state with no visible cause.

**Brand becomes an exact multi-select facet.** Its values and counts come free from the same aggregate pass — no enumeration endpoint, no new model. Two consequences accepted: `icontains` becomes exact, so `?brand=levi` stops substring-matching (blast radius is hand-typed URLs; the UI never had a brand control), and brand stays a `CharField` rather than being normalised to an FK, which would be a new model against this epic's standing rule.

**Repeated-key parameters**, `?color=Black&color=White`, read with `QueryDict.getlist()`. **Backward compatibility is free** — today's `?color=Black` parses to `["Black"]`, so every existing shared link keeps working with no shim. Rejected: CSV, which is prettier and safe for *this* catalog but needs `BaseCSVFilter` plus hand-written schema hints where repeated keys are handled natively by django-filter, DRF's browsable API and OpenAPI generation — and is a landmine the day a value contains a comma. `min_price`, `max_price` and `search` stay single-valued.

- [ ] `ProductPagination` → `PageNumberPagination`, `page_size = 12`
- [ ] `ProductFilter` facets accept multiple values via `BaseInFilter` / `MultipleChoiceFilter`
- [ ] `colors` / `sizes` filtered with `has_any_keys`, **not** `__contains`
- [ ] Facet counts computed per dimension against the other active filters, returned on the list response
- [ ] `OrderingFilter` with the five-entry allow-list; default `recommended`
- [ ] `brand` switched from `icontains` to exact, exposed as a facet
- [ ] `search` remains single-valued and untouched
