# 11.8 — Style Profile: Schema, API, and Prompt Injection

**What to build:** Give `User.style_preferences` a real schema, a write path, and a route into both the system prompt and product retrieval.

**Blocked by:** —

**Status:** ready-for-agent

## Decisions

**`style_preferences` exists and is used by nothing.** It is a `JSONField(default=dict, blank=True)` written by nothing and read by nothing. `UserSerializer` already *lists* it in `fields`, but `read_only_fields = fields` makes the whole serializer read-only. Readable, structurally unwritable.

**Schema is adapted to the catalog, not the design.** Four keys: **vibes** (array), **size** (single), **budget** (min/max in ₹), **gender**. `designs/page-profile` draws a Top Size of `Medium (M)` **and** a Bottom Size of `US 6` — a US numeric sizing system in an app whose entire catalog is lettered `XS`–`XXL` with one `sizes` array per product. The split has nothing to match and is dropped. Budget is denominated in ₹, not the design's `$150 – $600`. **Gender is added**, because it is the most filterable attribute in the catalog (Women 22 / Men 14 / Unisex 14) and the design omits it while asking for decorative preferences.

**The vibe vocabulary is closed.** The design's `+ ADD VIBE` free-text control is dropped for two reasons. **Security:** whatever lands in this field is interpolated into `SYSTEM_PROMPT`, so free text is user-controlled input entering the model's instructions — a prompt-injection surface. A closed list means the server only ever interpolates strings it chose. **Utility:** no catalog field describes a vibe and the descriptions are boilerplate, so a vibe can only steer prose or be folded into the embedded query; arbitrary strings make that noise.

**Validation lives in a DRF serializer; the field stays JSON.** Matches where this codebase already puts validation. Promoting the keys to columns would give SQL-filterability and a migration per preference — the wrong trade before anyone has used it. Reads must tolerate missing **and** unknown keys.

**Three injection mechanisms, deliberately different in strength.** A `{user_profile}` block in `SYSTEM_PROMPT`; vibes, gender and category intent folded into the text `ContextBuilder` embeds (the only path by which a vibe can influence retrieval at all); and a **hard filter on `gender` only**. A menswear kurta surfacing for a womenswear shopper is not a nuance, it is wrong; filtering halves a 50-product pool and `top_k` is 5, so there is room.

**Size and budget deliberately do not filter** — see the epic's decision. Both still reach the model through the prompt so it flags mismatches rather than hiding them.

**This requires `ContextBuilder` to receive the user, which it currently never does.** `build_product_context(user_message)` embeds the message and nothing else; retrieval is anonymous today. Three of these decisions depend on changing that signature.

**An empty profile says nothing.** The prompt block is omitted entirely when preferences are empty — which is the normal case, not the edge case. Plus one instruction permitting the stylist to invite the shopper to set preferences when a recommendation would clearly benefit, at most once per conversation. That invitation is the acquisition path: nobody fills in a preferences form because a form asked. Rejected: an explicit *"no preferences on file"* line, which invites the model to reference the absence far more often than intended.

**Read-only from the stylist's side.** The profile page is the only writer. Conversational write-back is out of scope (see the epic).

**`MeView` becomes `RetrieveUpdateAPIView`.** PATCH `/api/auth/me/` carries preferences alongside name; `read_only_fields` narrows from `fields` to `("id", "email")`, since email is the login identifier. Ownership is enforced by construction — `get_object` already resolves to `request.user`. Rejected: a separate `/preferences/` sub-resource, which is two round-trips and two cache entries for one JSON column on the current user.

- [ ] Preference serializer with typed fields and a closed vibe enum
- [ ] `MeView` → `RetrieveUpdateAPIView`; `read_only_fields = ("id", "email")`
- [ ] `{user_profile}` block added to `SYSTEM_PROMPT`, omitted when empty
- [ ] Prompt instruction to invite preference setup at most once per conversation
- [ ] `ContextBuilder` accepts the user; preferences folded into the embedded query
- [ ] `gender` hard-filters retrieval; size and budget do not
- [ ] Reads tolerate missing and unknown keys
