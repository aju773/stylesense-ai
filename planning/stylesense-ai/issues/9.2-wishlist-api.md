# 9.2 — Wishlist REST API

**What to build:** `/api/wishlist/` — list, save, and unsave, authenticated-only and scoped by user the same way cart items are (scope the lookup, never fetch-then-check, so someone else's id 404s indistinguishably from a missing one).

The interesting endpoint is the toggle: the heart on a product card is one control with two meanings, so `POST /api/wishlist/toggle/` takes a `product_id` and returns the resulting state rather than making the client know whether it is adding or removing. That is also what makes it idempotent under a double-click.

**Blocked by:** 9.1 — Wishlist Model

**Status:** done

- [x] Service layer owns the rules (`services/wishlist_service.py`) — views translate only
- [x] `GET /api/wishlist/` → saved items, newest first, with `ProductCardSerializer` nested and `source` on each
- [x] `POST /api/wishlist/toggle/` → `{product_id, source}` → `{saved: bool, item}`
- [x] `DELETE /api/wishlist/items/<id>/` → explicit unsave from the wishlist page
- [x] Inactive/nonexistent product → 400, matching the cart's `ProductUnavailable` shape
- [x] `source` only applies on create — re-hearting an AI pick from the catalog must not silently reclassify it
- [x] `in_stock` on each row — stock isn't on the product card and the page dims sold-out saves
- [x] Toggle returns only the touched row, not the whole list — a wishlist has no server-computed money for the client to get wrong

## Verified

- Anonymous `GET /api/wishlist/` → 401
- Save → 201 `{saved: true, product_id, item}`; toggle again → 200 `{saved: false, item: null}`
- Save with `source: "ai"` → listed under `ai`; unsaved and re-saved from the catalog → `manual`, which is where that save came from
- Unknown id and `is_active=False` product → 400 `"That product is no longer available."`; junk `source` → 400 from the serializer
- Second user: empty list, and `DELETE` on the first user's item id → 404 with the row untouched
- `DELETE` own item → 204; repeat → 404
- `stock=0` → `in_stock: false`
- 10 saved products list in **2 queries** — `select_related("product__category")` + `prefetch_related("product__images")`, no N+1 from `get_image_url`
- **Race:** two threads saving the same product on a barrier both returned `saved: true` with the *same* row id and left exactly one row — the loser's `IntegrityError` was caught inside the nested `atomic()` and answered with the winner's row instead of a 500
