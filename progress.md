## Recent Decisions
- Use `uv` for modern Python package management
- One conversation per sub-ticket
- Just-in-time slicing
- Mentor-only mode (sensei)
- Use Tailwind CSS v4 with Vite via `@tailwindcss/vite` (No config file)
- HttpOnly cookies for JWT (not localStorage)
- Token rotation + blacklisting on logout
- React Router v8 (was v7 at plan time, v8 is current)
- TanStack Query for server-state (useInfiniteQuery for paginated lists, useQuery for single resources)
- Cursor pagination over offset — handles real-time insertion without page drift
- Slug-based product URLs over IDs
- Dedicated `/api/categories/` endpoint for filter sidebar (DEC-012)
- Static filter values — show all possible, no cascading (DEC-013)
- REST chat endpoints stay alive alongside WebSocket (REST for history, WS for streaming only)
- `send_message_stream` yields uniform `{"event": ..., ...}` dicts (token/stream_start/stream_end) instead of mixing raw strings and dicts — one dispatch shape for every consumer, including 6.3's WebSocket consumer
- Postgres/Redis dev ports moved to 5434/6381 — host port collisions with an unrelated project (avanzo-pg on 5433) and a stale CHANNEL_LAYERS config (6380, nothing listened there)
- `CHANNEL_LAYERS` uses `channels_redis.pubsub.RedisPubSubChannelLayer`, not the default `RedisChannelLayer` — ChatConsumer never uses group_send/group_add, so pub/sub's simpler path is sufficient
- Pinned `redis<5` in `pyproject.toml` — redis-py 8.x raises `TimeoutError` on routine poll timeouts instead of returning `None`, which crashes channels_redis 4.3.0's listener loops (upstream: django/channels_redis#408)
- `ChatConsumer.receive_json` spawns streaming via `asyncio.create_task` (not a direct `await`) so the dispatch loop can pick up the next message while one is in flight — required for the `is_streaming` concurrency guard to be reachable at all, since Channels serializes `receive_json` calls otherwise. All `send_json` calls go through an `asyncio.Lock` since ASGI forbids concurrent `send()` calls on one connection
- Structured product data escapes the text stream via inline `[[product:id]]` markers, not tool calling or JSON mode. Tool calling would fork the provider interface (Gemini `function_declarations` vs Groq OpenAI `tools`) and break `AsyncGenerator[str]`; JSON mode would kill token streaming entirely. Markers are just text, so every provider "supports" them and the orchestrator fallback needs zero changes
- Markers stay in `ChatMessage.content` and are stripped at render time in `ChatBubble` — keeping them server-side is what lets history rebuild card ordering by first mention
- Marker ids are always validated against the DB before linking, which drops hallucinated ids for free — the prompt contract is best-effort, the persistence layer is not
- Product cards are serialized in `ChatService`, not in the consumer, so the WebSocket `products` event and the REST history endpoint return an identical card shape
- Groq model changed to `openai/gpt-oss-120b` — `llama-3.3-70b-versatile` now 404s on this account, so the fallback provider was silently dead before 7.1
- Mentor-only/sensei mode removed from `CLAUDE.md`; global `/caveman` output rule added at `~/.claude/CLAUDE.md`
- Cart is authenticated-only. A guest cart would require a session-keyed cart plus merge-on-login with conflict rules for duplicate `(product, size, color)` lines and cleanup of orphaned rows — a whole sub-ticket of work for a demo project where every interesting flow already needs an account
- `CartItem.size`/`color` are blank-not-null. Postgres treats `NULL != NULL`, so nullable columns would let the `(cart, product, size, color)` unique constraint pass for two "no size" lines of the same product — exactly the duplicate the constraint exists to prevent
- Cart lines store no price snapshot. The bag always reflects live catalog pricing; snapshotting belongs on the order at checkout (epic 10), or a cart quietly bills yesterday's price after a markdown
- **Cart uses TanStack Query, not Redux — a deliberate departure from ticket 08.** The cart is server-owned state (the server computes every total), and Query already has the exact optimistic primitive needed: `onMutate` applies the change, the snapshot in its context rolls it back on error. One shared `["cart"]` key gives the header badge, drawer, and page the same data with zero synchronisation code — which is what the "global client state" argument for Redux was meant to buy. Adding RTK would have put a second server-state cache beside Query with its own invalidation rules and real drift risk. Drawer open/closed is genuine client state and lives in a small `CartUIContext`
- Every mutating cart endpoint returns the **entire** recomputed cart, not just the touched row. The client replaces its state wholesale and never has to recompute money locally — the optimistic `estimateTotals` is a throwaway estimate for one frame, overwritten by the server's numbers on success
- Cart item routes scope their lookup by `cart__user=request.user` instead of fetching then checking ownership. Another user's item id is then indistinguishable from a nonexistent one — 404 either way, leaking nothing about what other carts hold
- `AuthContext` purges the `["cart"]` query cache on login, register, and logout. Without it, logging out and back in as someone else shows the previous user's bag from cache until the refetch lands
- Order placement is one transaction with the payment charge *inside* it. A real shop would reserve stock, charge outside the lock, and compensate on failure — that buys throughput at the price of a compensating path that can itself fail. Holding the locks across the gateway call is the deliberate trade here: the rollback is genuinely atomic, and that is the thing worth demonstrating
- Partial stock failure aborts the whole order rather than placing what it can. The 409 carries every failing line (product, variant, requested, available, and `insufficient_stock` vs `unavailable`), so the UI can annotate all the offending rows at once instead of the customer rediscovering them one at a time
- Stock is validated per *product*, summed across lines — the same shirt in M and L are two lines drawing on one pool, and validating them independently would sell two units of a one-unit product
- Product rows are locked in ascending pk order. Two orders sharing products would deadlock if they took the same rows in different sequences
- The mock gateway declines on demand (`tok_decline` sentinel) and sleeps ~1.2s. An always-succeeds stub would leave the stock-rollback path — the only genuinely interesting engineering in this epic — permanently unexercised and undemoable
- No `pending`/`failed` order status: neither is observable. The charge happens inside the placement transaction, so a decline rolls back and leaves no row to mark. An order exists only if it was paid for
- What `select_for_update()` actually buys, measured: without it, two concurrent placements both validate against stale stock and the second dies on Postgres's own `CHECK (stock >= 0)` — a 500. The column constraint is what prevents the oversell; the lock is what turns the crash into a correct 409
- Order placement returns 409, not 400, on a stock conflict — the request was well-formed and was valid when the customer sent it; the world moved underneath it
- `OrderItem.product` is `SET_NULL` with the product's name/brand/slug/image snapshotted alongside the price, so deleting a product empties the link without breaking order history. `Order.user` stays `CASCADE` to keep account deletion working, which a real shop would not do — orders are accounting records with a retention period
- Order placement gets **no** optimistic update, unlike every cart mutation. Cart changes are locally predictable and rollback-able; placement is not — success depends on stock the client hasn't seen and a payment that hasn't happened. Rendering a confirmed order before the server confirms it would be rendering a purchase that may not exist
- The three placement failures render as three different UIs because they are three different events: a decline is retryable on the spot, a 409 stock conflict sends the customer back to edit their bag, an empty bag redirects to `/cart`. `parsePlaceOrderError` maps status → a discriminated union so components switch on `kind`, never on status codes
- `usePlaceOrder` invalidates cart *and* products on **error** as well as success — a 409 means the catalog moved underneath the bag, so the retry should be against what is actually there
- No shipping address anywhere in epic 10. The orders design shows a Delivery Address block, but collecting one means an Address model, a form, and validation that demonstrate nothing the cart and auth forms don't already — so the block is dropped rather than faked
- Order status advances by a management command (`advance_orders`), not a timer or a derived value. There is no warehouse and no carrier webhook, so nothing would move an order past Processing on its own and the history page would show a column of identical rows. A derived-from-elapsed-time status was rejected: it is a value the DB doesn't hold, and it can't be filtered or queried
- `SiteHeader` gets a plain authenticated-only `Orders` link, not an account menu. Orders is the only account page that exists — Wishlist and Profile are still `<h1>` stubs, so a dropdown would be one real destination and two dead ones. That is the same mistake as the dead Checkout button epic 10 inherited; the menu belongs in whichever epic makes those pages real
- The orders design's **Reorder Items** and **Need Help?** buttons are omitted rather than rendered inert. Shipping controls with nothing behind them is precisely the debt 10.3 had to pay off
- Epic 08 built the app's first header/nav (`SiteHeader` + `AppLayout` layout route). There was no global chrome anywhere and `Products.tsx` had no navigation links at all, so the cart badge had nowhere to live; epics 09/10 need it too
- Wishlist has no parent row. `Cart` exists because a bag owns totals and per-bag state; a wishlist owns nothing but its set of items, so a `Wishlist` model would be a join with no columns worth reading — `WishlistItem` hangs straight off the user
- Wishlist uniqueness is `(user, product)`, not the cart's `(user, product, size, color)`. You save a product, not a variant; choosing a size is an add-to-bag decision made on the product page, and saving the same coat in three sizes is just the same coat three times
- `WishlistItem.product` is `CASCADE`, the opposite of `OrderItem`'s `SET_NULL` + snapshot. An order line is an accounting record that must outlive the catalog; a wishlist entry is a pointer *into* the live catalog, and a saved product that no longer exists is nothing the user could act on
- "AI Picked" is a `source` recorded when the user hearts a recommendation card in chat — the assistant never writes to the wishlist itself. An AI that silently saved things would make the tab a log of what the model said rather than a list of what the customer wants
- The heart is one control with two meanings, so the server owns which one happened: `POST /wishlist/toggle/` takes a product id and answers `{saved, product_id, item}`. The client never needs to know the current state to send the right request, so a card rendered before the product was saved in another tab can't get it wrong
- `toggle` catches the unique-constraint `IntegrityError` in a **nested** `atomic()` and returns the existing row. Two identical saves racing is a user who asked for it saved and got it saved — not a 500. The nested savepoint is what makes recovery possible at all; the violation would otherwise poison the outer transaction
- The wishlist page's unsave stays a separate `DELETE /items/<id>/` rather than reusing the toggle. On that page the heart only ever removes, and routing it through a toggle would turn an impatient double-click into remove-then-save-again
- Wishlist mutations return only the touched row, a deliberate departure from the cart's return-the-whole-bag rule. The cart returns everything because the server owns the money and the client must never recompute it; a wishlist has nothing computed, so resending every saved product on each heart-click is bytes spent telling the client what it already holds
- `WishlistItem.source` is set on create only. Unsaving an AI pick and re-saving it from the catalog records `manual` — that is where the new save actually came from, and the alternative is a row claiming a provenance no longer true
- The heart is a **sibling** of the product card's link, not a child. A `<button>` inside an `<a>` is invalid HTML, and nesting it means every save click has to fight the anchor's navigation with `preventDefault` on a target that may not be the button. `ProductCard` and the chat mini-card were both restructured for this
- Every heart reads the one `["wishlist"]` cache rather than per-product state, so saving from a catalog card immediately flips the same product's heart in the chat strip and on its detail page with no synchronisation code — the same argument that kept the cart on TanStack Query instead of Redux
- The optimistic wishlist row carries `in_stock: true` unconditionally. The hearts live on cards that don't know stock, and only the wishlist page reads the flag — by the time that page renders, the server's row has replaced the placeholder
- The product page's `♡ Add to Wishlist` button had been dead since 3.4, exactly like the Checkout button epic 10 inherited. 9.3 wires it rather than leaving a third epic to find it
- The two tabs filter the one cached list in the browser rather than issuing a per-tab request. The whole wishlist is already in the cache, so a round-trip would exist only to hide rows the client is holding
- "Move to Bag" navigates to the product page instead of adding. Every product in the seed catalog is sold in sizes and colors, so a direct add would have to invent a variant — and the picker that does it properly already exists one click away
- The card's CTA reveal is keyed on `[@media(hover:hover)]`, not a breakpoint. Tailwind v4 compiles `group-hover:` inside `@media (hover: hover)`, so on any touch device the reveal never fires — hiding it by default there (as the design's slide-up does) leaves the card's primary control permanently unreachable, and a touch tablet is wide enough that a `sm:` breakpoint would not have caught it
- Failed wishlist mutations invalidate the query as well as rolling back. A failed remove is usually a 404 meaning the row is genuinely gone, so the snapshot restores a card that does not exist — measured in the browser: gone at 17ms, restored at 38ms, removed again by the refetch at 61ms
- `SiteHeader` now carries Wishlist *and* Orders as plain links. Profile is still a stub, so a dropdown would still be two real destinations and one dead end

### Epic 11 — Beautiful StyleSense (planning)
- Playfair Display has **never rendered**. `index.css` is one line, `index.html` has no font link, and Tailwind never loads font files — not for `@theme` tokens, not for arbitrary values. All 28 `font-['Playfair_Display']` call sites across 17 files compile to valid, warning-free CSS and fall through to a system serif. The app's display typeface has been absent since 1.3
- Inter overrides Tailwind's own `--font-sans` rather than becoming a new `font-body` utility. Inter has zero call sites, so every unstyled paragraph renders in the system UI stack; a new utility would change nothing until someone touched hundreds of elements, whereas the override makes nine existing pages inherit it for free
- `@theme` stops at colours, fonts and the type scale. A v4 token overrides the default when the name collides, so declaring `--radius-lg` or `--shadow-md` would silently restyle every `rounded-lg` and `shadow-md` in the app. The type scale is safe because `--text-h1` / `--text-body-lg` collide with nothing
- `designs/design-system/DESIGN.md` contains **two conflicting palettes** — ~60 Material-3 tokens in the YAML frontmatter and 12 semantic colours in the markdown body. The app already implements the markdown set exactly (156 × `#1A1A1A`, 73 × `#777`); the frontmatter set is generator output wired to nothing
- One curated photo per product, with gallery views derived as imgix crops of that same photo. Three different stock photos of "linen trousers" are three different garments, so a gallery of them claims four views of one item while showing four separate items
- Pixabay ruled out as an image source: its API docs explicitly forbid permanent hotlinking, which is exactly what a URL in `ProductImage` is. Unsplash is also the only source with a documented resize pipeline on a permanent URL. The old `source.unsplash.com` endpoint is confirmed dead (sunset from 2024-06-11)
- `ProductSerializer` sends **no image field at all**, so the shop grid could not render a photo even with perfect data — and `ProductCard` reads `product.images?.[0]` from a payload that never contains the key. The queryset already prefetches `images`, so this is a one-line serializer fix, not a query change
- The shop filter moves to a top bar, deviating from `designs/page-shop`'s left rail. The app's pitch is that the AI narrows the catalog for you, and a permanent wall of facets contradicts it. The rail was the smaller problem anyway: every facet is a single-value `CharFilter`, so Black **and** White is impossible today
- `CursorPagination` retired for `PageNumberPagination`. Cursor pagination returns no `count` by design and constrains the ordering field — and the new filter bar needs a true result count beside facet counts, plus a free choice of sort. It solves drift under insertion on large mutating datasets; this catalog is 50 static rows
- Facets ride on the list response rather than a separate endpoint. Results and counts render together in one 56px bar, so two in-flight requests would mean a visible disagreement in the component whose job is telling the shopper the truth
- `colors`/`sizes` must be filtered with `has_any_keys`, **not** `__contains`. They are plain `JSONField`, not `ArrayField`, so `__overlap` does not exist — and `colors__contains=["Black","White"]` silently means AND, because Postgres `@>` requires the left array to hold *all* of the right's elements. The existing single-value code only works because it is always called with one element
- `Recommended` binds to `-rating, -created_at`. A true best-seller sort from `OrderItem` is computable and would be near-random on a demo database — worst on the default sort, the one nobody chooses and everybody sees
- Repeated-key filter params (`?color=Black&color=White`) are backward-compatible for free: today's `?color=Black` parses to `["Black"]`, so every existing shared link keeps working with no shim
- `backdrop-filter` on an ancestor creates a containing block, so `position: fixed` inside it resolves against that ancestor rather than the viewport. `SiteHeader` already uses `backdrop-blur-md` and the filter bar adds a second — the cart drawer, mobile filter sheet, and any future modal must be portalled to `document.body`. Found by rendering a sheet clipped inside the sticky bar
- Three overclaims cut for the same reason: the home page's "upload an inspiration photo" (no image input exists anywhere), the trust bar's "Secure Checkout" (a security assurance about a mock gateway), and the profile callout's "bespoke lookbooks" (nothing generates one). "Trending Now" over a rating sort survives — that is a merchandising label, not a capability claim nothing the shopper clicks can contradict
- Two fully-built features were going unadvertised and take the vacated trust-bar slots: order tracking and the wishlist. "Free Shipping" turned out to be literally true — `cart_service.calculate_totals` returns `Decimal("0.00")`
- The Edit becomes For Her / For Him / Unisex. The design's "Best Sellers" would have resolved to `-rating` — the same query Trending Now takes — putting two bands of identical products under different labels on one page
- The profile's Top Size / Bottom Size split is dropped: it is a US numeric sizing system in an app whose catalog is lettered `XS`–`XXL` with one `sizes` array per product. A `gender` preference is added instead, the most filterable attribute in the catalog and one the design never asks for
- The vibe vocabulary is closed, dropping the design's `+ ADD VIBE`. Free text there is user-controlled input interpolated into `SYSTEM_PROMPT` — a prompt-injection surface. A closed list also keeps the retrieval path open, since arbitrary strings folded into an embedded query are noise
- Only `gender` hard-filters retrieval. A size or budget mismatch is a *caveat* the stylist can speak to — "ideal, but only in L", "over budget and worth it" — and filtering them away deletes most of what a stylist is for. `stock = 0` is *unavailability*, so it filters too
- `ContextBuilder.build_product_context(user_message)` never receives the user; retrieval is anonymous today. Three style-profile decisions depend on changing that signature
- Chat rationales ride on `[[why:<id>]]` lines appended after the prose, leaving `[[product:id]]` untouched. Because `ChatMessage.content` already persists markers, reasons reparse from stored content on history load — **no schema change at all**. Extending the marker to `[[product:12|reason]]` would need a through-model on a plain M2M, and would make the reader watch half a marker render as literal text mid-sentence while streaming
- Streaming skeletons are sized by counting `[[product:id]]` markers as the text arrives. `ChatBubble` already parses them out and discards the count; using it lets the picks block reserve its true height before the `products` event lands
- Add to Bag on a chat card cannot be one click: `cart_service._validate_variant` rejects a line missing size or colour whenever the product has them, and every catalog product does. The card expands into a picker instead
- Chat confirms an add inline (`✓ In your bag` plus the header badge) rather than opening the cart drawer, deliberately departing from `ProductDetail`. That pattern was set where the shopper is finished; a chat message holds up to five picks and a drawer covers the ones still unread
- The profile's budget control is preset chips, not the design's slider. Budget is advisory — nothing consumes the number precisely — so `₹2,500–₹7,000` and `₹3,000–₹6,000` behave identically, and the slider's precision has no consumer. It would have cost a custom dual-range control the project does not own
- The profile drops the account nav entirely. With Security out of scope it reduces to two real tabs plus My Orders and Wishlist, which are top-level routes already in the header — half the entries would only navigate away
